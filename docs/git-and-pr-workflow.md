# Git / PR / 리뷰 워크플로우

여럿이 같은 `main`에 안전하게 합치기 위한 규칙. 커밋 메시지 규칙은 루트
[`CLAUDE.md`](../CLAUDE.md)(Conventional Commits 한글, 트레일러 금지)를 따른다.

## 브랜치
- `main`은 항상 배포·빌드 가능한 상태로 보호한다. **`main`에 직접 push 하지 않는다.**
- 작업은 브랜치에서: **`<type>/<kebab-요약>`** — type은 커밋 prefix와 동일.
  - 예: `feat/notification-throttle`, `fix/url-404`, `docs/code-guide`, `refactor/url-port`
- 브랜치는 짧게 살린다. 오래 두면 충돌·리베이스 비용이 커진다.

## PR 규칙
- **하나의 PR = 하나의 논리적 변경.** 리뷰 가능한 크기(대략 400줄 이내 목표)로 쪼갠다.
- 제목은 커밋 컨벤션을 따른다: `feat: 알림 스로틀링 추가`.
- 본문은 [PR 템플릿](../.github/pull_request_template.md)을 채운다(무엇을·왜, 테스트, 문서 영향).
- 작업 중이면 **Draft PR**로 올려 방향을 빨리 공유한다.
- CI(빌드·테스트)가 초록이어야 머지 대상이 된다. → 자동 게이트는 후속 도입 항목.

## 리뷰
**리뷰어 체크리스트** (코드가이드 준수가 핵심):
- [ ] 신규 코드가 [코드 가이드](./code-guide/README.md) 6원칙을 따른다(도메인 순수성, 불변식, 에러 중앙화 등).
- [ ] 변경에 **테스트가 동반**된다(버그 수정은 재현 테스트 포함). → [TDD](./code-guide/03-tdd.md)
- [ ] DB 변경 시 마이그레이션 규칙 준수: `V{n}__설명.sql` 신규 추가, 기존 수정 금지.
- [ ] 네이밍이 [용어집](./glossary.md)의 유비쿼터스 언어와 일치한다.
- [ ] 시크릿·민감정보가 코드/로그/PR에 노출되지 않는다. → [로깅](./code-guide/05-logging.md)
- [ ] 공개 API 변경이 하위호환을 깨지 않거나, 깬다면 의도가 설명돼 있다.

**리뷰 에티켓**
- 코멘트는 **근거와 함께**. 단순 취향 지적은 `nit:` 접두사로 구분(머지 차단 아님).
- "왜 안 되는지"보다 "어떻게 하면 좋은지"를 제안한다.
- 작성자는 모든 코멘트에 응답(반영 또는 사유)한 뒤 resolve 한다.

## 머지
- **Squash merge를 기본**으로 한다(논리 단위 1커밋, main 히스토리 선형 유지). 머지 커밋 제목은
  Conventional Commits 형식.
- 머지 후 **원격 작업 브랜치를 삭제**한다.
- 머지 전 `main` 변경을 반영(rebase 또는 merge)해 CI를 다시 통과시킨다.

## DB 마이그레이션 충돌 주의 (협업 함정)
- 두 PR이 동시에 같은 버전(`V2__...`)을 추가하면, **나중에 머지되는 PR이 다음 번호로 리넘버**한다.
  (이미 적용된 마이그레이션은 절대 수정하지 않는다.)
- 리뷰어는 머지 시점에 버전 번호 충돌 여부를 확인한다.

## 문서 동기화 (코드와 문서가 어긋나지 않게)
PR 템플릿의 "문서 영향" 체크리스트를 강제한다:
- 도메인 규칙/아키텍처 결정 변경 → [ADR](./adr/) 추가·갱신
- 새 용어 도입 → [용어집](./glossary.md) 갱신
- 규약 변경 → 관련 `CLAUDE.md` 갱신
