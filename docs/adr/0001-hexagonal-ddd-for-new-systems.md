# ADR 0001: 신규 시스템은 헥사고날+DDD, 기존 시스템은 레이어드 유지

## 상태
Accepted (2026-06-22)

## 컨텍스트
- 이 저장소는 시스템 설계 학습용 모노레포다. 기존 `url-shortener`, `notification-system`은
  레이어드(Controller → Service → Repository) 구조로 이미 구현·완료되어 있다.
- 도메인 표현력·테스트 용이성·어댑터 교체 가능성을 높이기 위해 헥사고날(포트&어댑터) + DDD
  도입을 검토했다.
- 동시에, 이미 완료된 학습 산출물을 다시 갈아엎는 비용과 "한 레포 두 스타일"의 일관성 문제를
  함께 고려해야 했다.

## 결정
- **신규 코드/시스템은 헥사고날 아키텍처 + DDD를 따른다.** 6대 원칙과 패키지 구조는
  `docs/code-guide/`에 정의한다.
- **기존 `url-shortener`, `notification-system`은 레이어드 구조를 유지한다.** 큰 기능을 새로
  붙일 때 점진 이관은 허용하되 강제하지 않는다.

## 결과
- 코드: `docs/code-guide/01-hexagonal-architecture.md` (패키지 구조·의존성 규칙), 신규 시스템부터 적용
- 컨벤션: 루트 `CLAUDE.md`의 "구조" 항목과 "코드 작성 가이드" 섹션에 반영
- 테스트: 신규 도메인은 스프링 없는 빠른 단위 테스트로 검증(`docs/code-guide/03-tdd.md`)
- 감수하는 비용:
  - 레포 안에 두 가지 스타일이 공존 → 작업 전 "신규냐 기존이냐"를 먼저 구분해야 한다.
  - 도메인 모델 ↔ JPA 엔티티 분리로 매핑 보일러플레이트가 생긴다(단순 CRUD는 예외 허용).

## 대안
- **전면 이관(기존도 헥사고날로 재작성)** → 기각: 완료된 학습 산출물을 다시 쓰는 비용 대비
  효용이 낮다.
- **레이어드 유지(헥사고날 도입 안 함)** → 기각: 도메인 복잡도가 커질 때 표현력·테스트 격리에
  한계.
- **포트 없이 서비스에 도메인 로직만 강화** → 보류: 포트 경계가 없으면 어댑터 교체·테스트 격리
  이점이 약하다. 도메인 복잡도가 충분히 큰 신규 시스템에서 재검토.
